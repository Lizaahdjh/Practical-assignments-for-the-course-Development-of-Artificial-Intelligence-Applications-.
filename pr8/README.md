# ПР8. Виклик інструментів мовною моделлю

Помічник клієнта інтернет-магазину **«Сузірʼя»**, який відповідає на питання про замовлення, товари, доставку та повернення, викликаючи функції внутрішнього сервісу магазину як інструменти моделі.

Модель лише **пропонує** виклик. Виконує код — і лише те, що пройшло перевірку: чи існує такий інструмент, чи відповідають аргументи схемі, чи належить замовлення саме цьому клієнтові та чи дозволена операція.

## Мета

* Описати інструменти схемами так, щоб модель правильно їх обирала.
* Перевіряти кожен виклик до виконання: назву, JSON, схему та зміст.
* Визначати клієнта на рівні коду, а не моделі.
* Повертати моделі лише необхідні поля.
* Обробляти помилки сервісу як результат інструмента.
* Перевірити помічника на звичайних, граничних і зловмисних питаннях.

## Що змінилося порівняно з ПР6

| Було в ПР6                | Стало в ПР8                                 |
| ------------------------- | ------------------------------------------- |
| Відповіді за документами  | Відповіді за живими даними сервісу магазину |
| Пошук за текстом          | Виклик інструментів (tool calling)          |
| Одна відповідь моделі     | Цикл «модель → виклики → модель»            |
| Правила лише в коді       | Схема параметрів + перевірка змісту         |
| Помилки сервісу неможливі | Обробка `ShopError` як результату           |

### Основні модулі

* `main.py` — веб-рівень: `/api/customers`, `/api/tools`, `/api/ask`, `/api/reset`.
* `tools.py` — описи інструментів, перевірка аргументів і виконання.
* `llm.py` — системна інструкція та виклик моделі з інструментами.
* `assistant.py` — цикл «модель → інструменти → модель».
* `index.html` — сторінка вибору клієнта, введення питання та перегляду журналу викликів.
* `shop/service.py` — внутрішній сервіс магазину.
* `shop/data/` — клієнти, замовлення, товари, склад і тарифи.
* `eval/run.py` — запуск тестового набору та формування результатів.

## Інструменти, доступні моделі

У файлі `app/tools.py` описи інструментів задані у форматі OpenAI tools із JSON Schema параметрів.

| Інструмент        | Що робить                            |
| ----------------- | ------------------------------------ |
| `list_orders`     | Список замовлень поточного клієнта   |
| `get_order`       | Деталі замовлення клієнта за номером |
| `search_products` | Пошук у каталозі за словами          |
| `get_product`     | Картка товару за артикулом           |
| `get_stock`       | Наявність товару на складі           |
| `delivery_quote`  | Вартість і строк доставки            |
| `create_return`   | Створення заявки на повернення       |

### Що не доступно моделі

Адміністративні операції сервісу не описані в `specs()`, тому модель про них не знає:

* `issue_refund` — повернення коштів;
* `set_order_status` — зміна статусу;
* `update_price` — зміна ціни;
* `add_bonus` — нарахування бонусів.

Також модель не має доступу до `cancel_order`. Сервіс підтримує цю операцію, але клієнт повинен виконувати скасування через особистий кабінет.

## Захист доступу до даних

### Ідентифікація клієнта

`customer_id` не є аргументом жодного інструмента.

Він береться з `Context`, який формує веб-рівень на основі `customer_id` запиту. Модель цього значення не бачить і не може його змінити.

### Захист замовлень

Чужі замовлення не читаються. Перевірка `_ensure_own_order` визначає, чи належить замовлення клієнтові з поточного `Context`.

### Санітизація результатів

Перед передачею результатів моделі видаляються службові та потенційно небезпечні поля.

Зокрема, `_pick_order_fields` і `_pick_product` прибирають:

* `internal_note`;
* `card_last4`;
* `customer_id`;
* повні контактні дані;
* підозрілі «примітки для AI».

## Робота `assistant.answer`

Основний цикл має вигляд:

```text
модель
   ↓
аналіз відповіді
   ↓
виклик інструмента
   ↓
перевірка аргументів
   ↓
виконання інструмента
   ↓
результат інструмента
   ↓
модель
   ↓
остаточна відповідь
```

У коді використовується обмеження кількості раундів:

```text
while rounds < MAX_ROUNDS:
    викликати модель з описами інструментів

    якщо викликів немає:
        повернути відповідь

    додати повідомлення моделі в історію

    для кожного виклику:
        перевірити та виконати інструмент
        додати результат як role="tool"
```

Якщо ліміт раундів вичерпано, виконується останній виклик із `tool_choice="none"`, після чого повертається відповідь або запасне повідомлення.

## Ключові рішення

| Питання                         | Рішення                                       |
| ------------------------------- | --------------------------------------------- |
| Максимальна кількість звертань  | `TOOL_MAX_ROUNDS=3`                           |
| Паралельні виклики              | Виконуються послідовно                        |
| Повідомлення моделі з викликами | Додаються в історію як є                      |
| Ліміт раундів                   | Останній виклик із `tool_choice="none"`       |
| Збій моделі                     | Один раз виконується спроба без інструментів  |
| Час                             | Час моделі та інструментів вимірюється окремо |
| Токени                          | Сумуються за всі звертання                    |

## Обробка помилок сервісу

`app/tools.py` перехоплює `ShopError` і повертає його як `ToolResult`.

| Помилка сервісу   | `error.code`      | Що робить модель                               |
| ----------------- | ----------------- | ---------------------------------------------- |
| `NotFound`        | `not_found`       | Повідомляє клієнтові, що об'єкт не знайдено    |
| `InvalidRequest`  | `invalid_request` | Просить уточнити дані або пояснює проблему     |
| `PolicyViolation` | `policy`          | Пояснює правила магазину                       |
| `Unavailable`     | `unavailable`     | Повідомляє про тимчасову недоступність сервісу |

**Важливо:** помилка сервісу є **результатом інструмента**, а не збоєм HTTP-запиту. Модель отримує цей результат і переказує його клієнтові, не вигадуючи причину.

Трасування стека та внутрішні повідомлення винятків не передаються клієнтові.

## Налаштування `.env`

```env
# ---- Мовна модель ----
LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
LLM_API_KEY=<ваш ключ з Google AI Studio>
LLM_MODEL=gemini-3.1-flash-lite
LLM_TEMPERATURE=0
LLM_MAX_TOKENS=800
LLM_TIMEOUT=30

# ---- Інструменти ----
TOOL_MAX_ROUNDS=3

# ---- Сервіс магазину ----
SHOP_TODAY=2026-10-06
SHOP_DELAY_MS=0
SHOP_FAILURE_RATE=0
```

Ключ доступу — той самий, що використовувався у ПР3–ПР7. Його можна перенести з `pr7/.env`.

Модель повинна підтримувати **виклик інструментів**. `check_env.py` перевіряє відповідність налаштувань.

Якщо `check_env.py` показує `404`, потрібно перевірити значення `LLM_MODEL` у `.env`.

## Як користуватися сторінкою

1. **Оберіть клієнта** у списку. Це замінює вхід до особистого кабінету.
2. Введіть питання.
3. Натисніть **«Запитати»**.
4. Перегляньте:

   * відповідь помічника;
   * журнал викликів;
   * назви інструментів;
   * аргументи, передані моделлю;
   * статус виклику (`виконано` / `відхилено` / `помилка`);
   * результат, повернутий моделі;
   * службові дані.
5. У службових даних доступні:

   * використана модель;
   * кількість звертань;
   * час роботи моделі;
   * час роботи інструментів;
   * кількість токенів.
6. У блоці **«Інструменти, які бачить модель»** можна переглянути точний набір інструментів, доступний моделі.

Якщо модель обирає неправильний інструмент, насамперед потрібно перевірити саме цей список.

## Перевірка на наборі питань

Спочатку створіть власний набір із прикладу:

```powershell
copy eval\questions.example.json eval\questions.json
```

Після цього запустіть оцінювання:

```powershell
.venv\Scripts\python.exe eval\run.py
```

Скрипт обробляє **15+ питань** і формує:

* `eval/results.json` — журнали викликів і відповіді для кожного питання;
* `eval/findings.md` — зведені таблиці та місця для висновків.

### Власні питання

До набору потрібно додати **5 власних питань**:

* 2 звичайні — наприклад, питання про наявність іншого товару;
* 3 граничні:

  * спроба підміни клієнта;
  * спроба виконати заборонену операцію;
  * порожній або некоректний аргумент.

## Експеримент «одна зміна»

Необхідно змінити **одну** річ у `.env` або коді.

Наприклад:

```text
TOOL_MAX_ROUNDS=3 → 2
```

Або:

* прибрати фразу «магазин доставляє лише по Україні» з інструкції;
* додати обрізання `description` у `_pick_product`.

Після зміни повторно запустити:

```powershell
.venv\Scripts\python.exe eval\run.py
```

Порівняти:

* правильність вибору інструментів;
* правильність аргументів;
* кількість звертань;
* кількість токенів;
* час виконання.

## Прогін із відмовами сервісу

Для перевірки поведінки при тимчасовій недоступності сервісу у `.env` встановити:

```env
SHOP_FAILURE_RATE=0.3
SHOP_DELAY_MS=500
```

Після цього:

```powershell
.venv\Scripts\python.exe eval\run.py
```

Частина викликів може отримати:

```text
error: "unavailable"
```

У такому випадку модель повинна повідомити клієнтові, що сервіс тимчасово недоступний.

Це **нормальний результат тестування**, а не збій застосунку.

## Обробка збоїв

| Збій                         | HTTP | Клас                             |
| ---------------------------- | ---: | -------------------------------- |
| Порожнє питання              |  400 | `HTTPException`                  |
| Занадто довге питання        |  400 | `HTTPException`                  |
| Невідомий клієнт             |  404 | `HTTPException`                  |
| Сервіс магазину недоступний  |  503 | `HTTPException`                  |
| Таймаут моделі               |  504 | `llm.LLMTimeoutError`            |
| Перевищення лімітів          |  429 | `llm.LLMRateLimitError`          |
| Недоступність сервісу моделі |  503 | `llm.LLMServiceUnavailableError` |
| Помилка автентифікації       |  502 | `llm.LLMAuthError`               |
| Несподівана помилка          |  500 | `HTTPException`                  |

**Важливо:** помилка інструмента, наприклад «не знайдено» або «операція не дозволена», не є HTTP-помилкою. Вона повертається моделі як результат інструмента, після чого модель пояснює ситуацію клієнтові.

## Безпека

* API-ключ зберігається лише у `.env`, який не повинен потрапляти до репозиторію.
* Клієнта визначає код через `Context.customer_id`, а не модель.
* Чужі замовлення не читаються та не змінюються.
* Перевірка належності замовлення виконується через `_ensure_own_order`.
* Адміністративні операції не описані в `specs()`, тому модель не має до них доступу.
* Службові поля не передаються моделі:

  * `internal_note`;
  * `card_last4`;
  * `customer_id`;
  * `email`;
  * `phone`.
* Непряма ін'єкція в описі товару обмежується кодом `_pick_product` та системною інструкцією.
* Модель не може самостійно змінити ідентифікатор клієнта.

## Архітектура

```text
Клієнт
   │
   ▼
Веб-рівень
   │
   │ Context.customer_id
   ▼
Модель
   │
   │ пропонує tool call
   ▼
tools.py
   │
   ├── перевірка назви
   ├── перевірка JSON
   ├── перевірка схеми
   ├── перевірка прав доступу
   └── виконання
          │
          ▼
     shop/service.py
          │

      ToolResult
          │
          ▼
```

Головний принцип системи:

> **Модель пропонує дію, але не має права самостійно виконати її. Остаточна перевірка та виконання належать програмному коду.**

## Висновок

ПР8 реалізує клієнтського помічника, який використовує **tool calling** для отримання актуальних даних із внутрішнього сервісу магазину.

Основний принцип архітектури полягає в розділенні відповідальності: модель визначає, який інструмент може бути потрібним, але програмний код перевіряє назву, аргументи, схему, права доступу та дозволеність операції перед її виконанням.

Такий підхід дозволяє контролювати доступ до даних клієнтів, приховувати службову інформацію, обмежувати доступ моделі до адміністративних операцій та безпечно обробляти помилки внутрішнього сервісу.
