## 1. Які події записуються в журнал?

### Події журналу

| Подія | Рівень | Опис |
|---|---|---|
| `http.request` | INFO | HTTP-запит: метод, шлях, статус і тривалість |
| `draft.created` | INFO | Створення чернетки |
| `llm.attempt` | INFO / WARNING / ERROR | Кожна спроба звернення до провайдера |
| `draft.done` | INFO | Успішне завершення, кількість спроб, провайдер, вартість і кешування |
| `draft.failed` | ERROR | Остаточний збій |
| `draft.cancelled` | INFO | Скасування операції |
| `budget.warning` | WARNING | Досягнення 80 % денного ліміту |
| `rate_limit.rejected` | WARNING | Відхилення запиту з HTTP 429 |

### Дані, які не записуються

- Ключ доступу `LLM_API_KEY` та заголовок `Authorization`.
- Текст звернення клієнта.
- Факти з іменами та номерами замовлень.
- Повний prompt.
- Фрагменти потоку `delta`, які передаються через SSE.

### Результати перевірки журналу

У сценарії 2 було створено 10 чернеток.

| Показник | Значення |
|---|---:|
| Загальна кількість записів | 598 |
| `llm.attempt` | 16 |
| `draft.created` | 10 |
| `draft.done` | 9 |
| `draft.failed` | 1 |
| Бізнес-записи загалом | 36 |
| Середня кількість бізнес-записів на чернетку | 3,6 |
| HTTP-записи | 562 |

Більшість записів `http.request` виникла через опитування `GET /api/drafts/{id}` кожні 0,25 секунди у `replay.py`. У реальному застосунку використання SSE дозволяє зменшити кількість таких записів.

Якби журнал записував кожен фрагмент генерації, поле `events` у чернетці могло б містити 330–500 записів. Це збільшило б кількість записів приблизно у 90–140 разів.

## 2. Траса чернетки з трьома спробами

Приклад траси `draft=9937cc4f` зі сценарію 2:

```text
llm.attempt attempt=1 status=error kind=unavailable
llm.attempt attempt=2 status=error kind=unavailable
llm.attempt attempt=3 status=ok cost=0.000308
draft.done attempts=3 cost=0.000308 cached=false
```

Повна траса містить такі події:

```text
http.request POST /api/drafts status=202
draft.created draft_id=9937cc4f request=d02 client=replay fresh=true
llm.attempt attempt=1 status=error kind=unavailable
llm.attempt attempt=2 status=error kind=unavailable
llm.attempt attempt=3 status=ok
draft.done attempts=3
```

Траса формується за двома ідентифікаторами:

- `draft_id` — для внутрішньої траси чернетки.
- `request_id` — для відстеження HTTP-запиту.

### Передавання `request_id` у фоновий потік

У `jobs.start` використовується `contextvars.copy_context()`, після чого потік запускається через `ctx.run(runner)`. Це дає змогу передати `telemetry.request_id_var` із HTTP-потоку у фоновий.

Додатково `request_id` зберігається в `Request.metadata`, а `gateway._log_attempt` записує його в кожну подію `llm.attempt`.

Приклад JSON-запису:

```json
{
  "event": "llm.attempt",
  "draft_id": "9937cc4f",
  "request": "d02",
  "attempt": 3,
  "provider": "mock",
  "model": "mock-1",
  "prompt_version": "drafts-v1",
  "status": "ok",
  "duration_ms": 13898.0,
  "queue_ms": 0.0,
  "first_token_ms": 600.5,
  "prompt_tokens": 253,
  "completion_tokens": 93,
  "cost": 0.000308,
  "cost_estimated": false,
  "cached": false,
  "fallback": false
}
```

## 3. Захист конфіденційних даних

У журналі не зберігаються ключі доступу, текст звернення клієнта, персональні дані та повний prompt.

Захист забезпечується трьома рівнями:

1. `gateway._log_attempt` формує `extra` лише з дозволених полів.
2. `drafting.build_request` зберігає в `metadata` тільки довжину запиту, кількість фактів, хеш тексту та версію prompt.
3. `telemetry.JsonFormatter` додає лише визначені поля: `ts`, `level`, `logger`, `event`, `request_id` та `extra`.

### Перевірка журналу

Для пошуку конфіденційних даних використовувалася команда PowerShell:

```powershell
Select-String -Path logs\archive\s02.jsonl -Pattern `
  "Бондар|Коваль|Мельник|10412|10421|10458|10463|10377|20450012345678|R-5001|R-5002|AIza|sk-|Bearer"
```

Результат: **0 збігів**. Результат перевірки збережено у `eval/notes/03-grep.txt`.

Стек помилки записується лише в журнал за допомогою `exc_info` та `log.exception`. Користувачеві повертається повідомлення без стека викликів.

## 4. Версія prompt

Для контролю версій використовуються два значення:

- `PROMPT_VERSION = "drafts-v1"` — читабельна версія, яку розробник змінює вручну.
- `_PROMPT_HASH` — перші 8 символів SHA-256 від `SYSTEM_PROMPT`.

Версія prompt використовується в `Request.metadata`, подіях `llm.attempt` та `/api/health`.

Ключ кешу формується з повідомлень `messages`, тому зміна системного prompt змінює ключ і призводить до промаху кешу, навіть якщо розробник забув оновити `PROMPT_VERSION`.

Ручна версія потрібна для аналізу змін якості генерації після оновлення prompt.

## 5. Розрахунок вартості запитів

| Випадок | Джерело вартості | Результат |
|---|---|---|
| Звичайний виклик з `usage` | `costs.estimate(usage)` | Точний розрахунок, `cost_estimated=false` |
| Відсутність `usage` | `costs.estimate(None, text=...)` | Оцінка, `cost_estimated=true` |
| Влучання в кеш | Вартість дорівнює нулю | Бюджет не списується |
| Збій до початку генерації | Вартість невідома або дорівнює нулю, якщо токени не витрачено | Залежить від етапу збою |

Приклади:

- Звичайний виклик: 262 вхідні токени, 97 вихідних токенів, вартість `$0.000321`.
- Невдалі спроби з частковим текстом у сценарії 18: 9 спроб, сумарна оцінка `$0.000027`.
- Кешування у сценарії 8: 5 влучань, вартість кожного — `$0`.
- Найдорожча чернетка у сценарії 8: `d04` — `$0.000447`.
- Середня вартість чернетки: `$0.000340`.

### Вартість у потоковому режимі

`check_env.py` підтвердив, що Gemini через OpenAI-сумісний API повертає `usage` в останньому фрагменті потоку за умови використання `stream_options={"include_usage": True}`.

У `openai_compat.stream` повертається `Chunk(text="", usage=...)`, після чого `gateway._try_once` зберігає дані про використані токени.

## 6. Ключ кешу

Ключ кешу формується в `cache.make_key` за допомогою SHA-256 від JSON-структури.

### Дані, які входять у ключ

- `provider` — провайдер.
- `model` — модель.
- `prompt_version` — версія prompt.
- `messages` — системне повідомлення та повідомлення користувача.
- `temperature` — температура генерації.
- `max_tokens` — максимальна кількість токенів.

### Дані, які не входять у ключ

- `client` — ідентифікатор клієнта.
- `draft_id` — ідентифікатор чернетки.
- `request_id` — ідентифікатор запиту.
- Час створення.
- `fresh` — ознака примусового оновлення.

### Додаткові параметри кешування

- `CACHE_TTL_SECONDS=3600` — час життя запису становить одну годину.
- `fresh` оминає `cache.get`, але `cache.put` виконується, щоб нова чернетка замінила попередній запис.
- Об'єднання одночасних однакових запитів у польоті не реалізовано. У сценарії з п'ятьма одночасними запитами всі п'ять могли б отримати промах кешу, якщо перший запит ще не завершився.

## 7. Порівняння роботи з кешем і без нього

Сценарії 7 та 8 запускалися з параметрами `--seed 1`, 12 замовлень і `repeat=0.5`.

Послідовність замовлень:

```text
d03 d02 d02 d08 d04 d03 d07 d02 d05 d04 d02 d01
```

| Метрика | Без кешу (s07) | З кешем (s08) | Різниця |
|---|---:|---:|---:|
| Замовлення | 12 | 12 | — |
| Звернення до провайдера | 12 | 7 | −5 (−42 %) |
| Кеш-влучання | 0 | 5 | +5 |
| Токени, вхід + вихід | 4424 | 4424 | 0 |
| Вартість усіх чернеток | $0.004078 | $0.004078 | 0 |
| Фактичні витрати бюджету | $0.004078 | $0.002709 | −$0.001369 |
| Медіанний час | 16,16 с | 14,07 с | −2,09 с |
| Час p95 | 21,09 с | 16,27 с | −4,82 с |
| Сумарний час | 188,9 с | 110,6 с | −78,3 с (−41 %) |

`cost_total` однаковий, оскільки `replay.summarize` сумує вартість усіх завершених чернеток, включно з кешованими.

Проте кешовані відповіді не списують бюджет: для них `budget.record()` не викликається. Фактичні витрати зберігаються в `state/budget.json`.

У тесті було отримано 5 кеш-влучань із 12 запитів — 42 %. Це результат синтетичного потоку з 50 % повторів, тому в реальних умовах частка може бути меншою.

## 8. Контроль денного бюджету

Контроль бюджету реалізований на трьох рівнях.

1. **Перевірка:** `budget.check()` у `gateway._generate_with` перед кожною спробою провайдера.
2. **Облік:** `budget.record(cost)` після спроби, включно з частковими результатами та невдалими викликами, якщо витрати вже виникли.
3. **Збереження стану:** файл `state/budget.json`, який оновлюється атомарно через `mkstemp` та `os.replace`.

Стан бюджету зберігається після перезапуску застосунку. Межа доби визначається за локальним часом, а час скидання записується в `resets_at` у форматі ISO.

### Сценарій 13: перевищення бюджету

За параметра `BUDGET_DAILY_USD=0.003` було виконано 20 замовлень.

- Замовлення 1–9 завершилися зі статусом `done`.
- Сумарні витрати становили `$0.003018`.
- Бюджет було вичерпано.
- Замовлення 10–20 завершилися з `kind=budget`.
- Для заблокованих замовлень виклики провайдера не виконувалися.

### Сценарій 14: збереження після перезапуску

Після перезапуску три замовлення завершилися з `kind=budget`, без викликів провайдера.

У файлі `state/budget.json` зберігався стан:

```json
{
  "day": "2026-10-23",
  "spent": 0.003018
}
```

### Перевищення через паралельні запити

У сценарії з двома одночасними запитами обидва могли б пройти перевірку залишку бюджету. Це створює ризик невеликого перевищення.

Для виробничого застосунку доцільно реалізувати резервування очікуваної вартості перед викликом провайдера.

### HTTP-відповідь при вичерпанні бюджету

Застосунок повертає HTTP 429, заголовок `Retry-After`, `kind=budget` і `request_id`.

Оператор отримує повідомлення про вичерпання бюджету та час його відновлення.

Кешовані відповіді залишаються доступними, оскільки перевірка бюджету виконується після перевірки кешу. Запасний провайдер `mock` також враховується в бюджеті за `MOCK_BILLABLE=1`, тому його не можна використовувати для обходу ліміту.

## 9. Аналіз результатів тестування

### Сценарій 2: повторні спроби

За параметрів `failure_rate=0.6` і 10 чернеток:

- Найповільший виклик тривав 21 012 мс.
- `queue_ms=0`.
- `first_token_ms=601`.
- Час після першого токена становив приблизно 20 411 мс.
- Найчастішим типом збою був `unavailable` — 7 спроб.
- Повторні спроби допомогли завершити 3 із 4 чернеток, у яких перша спроба була невдалою.
- Одна чернетка не завершилася навіть після трьох спроб.
- Вартість невдалих спроб, що завершилися до генерації токенів, становила `$0`.

Значна частина часу витрачалася на генерацію, а не на очікування в черзі.

### Сценарій 13: бюджет

Загальні витрати становили `$0.003018` за ліміту `$0.003`. Перевищення дорівнювало `$0.000018`, тобто приблизно 0,6 % ліміту.

Це показало, що без попереднього резервування вартості можливе незначне перевищення бюджету.

### Сценарій 18: переривання потоку

- 3 замовлення.
- 3 спроби на кожне замовлення.
- 9 спроб провайдера загалом.
- Усі замовлення завершилися з `kind=unavailable`.
- Деталі містили `partial_text_len=N`.
- Оцінена вартість становила `$0.000027`.

Цей тест показав необхідність враховувати витрати навіть тоді, коли генерація завершилася помилкою.

### Сценарій 8: кешування

П'ять кеш-влучань скоротили час обробки з 14–21 секунди до 0,27–0,31 секунди.

Загальна економія часу становила 78,3 секунди, або приблизно 41 % на 12 замовленнях.

## 10. Виявлені проблеми та виправлення

Під час перевірки було виконано кілька ітерацій виправлень.

### 10.1. Облік вартості часткових відповідей

**Проблема:** у сценарії 18 вартість невдалих спроб відображалася як `null`, хоча частина токенів уже була витрачена.

**Виправлення:** у `gateway._generate_with` додано запис `cost` та `cost_estimated` для часткових спроб. У деталях зберігається `partial_text_len`.

Результат: замість нульової вартості враховується оцінена сума `$0.000027`.

### 10.2. Неправильне округлення бюджету

**Проблема:** повідомлення про вичерпання бюджету показувало `0.00`, оскільки використовувалося форматування `f"{limit:.2f}"`.

**Виправлення:** точність змінено на чотири знаки після коми:

```python
f"{limit:.4f}"
```

Тепер оператор бачить точніше значення ліміту.

### 10.3. Хибні попередження про відсутні номери замовлень

**Проблема:** `drafting.check` перевіряв усі номери з `facts`, зокрема номери з негативних тверджень.

**Виправлення:** додано пропуск фактів із маркерами:

- `не поширюється`;
- `не підлягає`;
- `не стосується`.

Це зменшило кількість хибних попереджень.

### 10.4. Надлишкові записи HTTP-клієнта

**Проблема:** логери `httpx` та `httpcore` створювали зайві технічні записи в журналі.

**Виправлення:** у `telemetry._silence_noisy_loggers()` додано вимкнення логерів, назви яких містять `httpx` або `httpcore`.

### 10.5. Неправильний підрахунок повторних спроб

**Проблема:** `analyze.repeated` показував 0 чернеток із кількома спробами, оскільки враховував тільки спроби зі статусом `ok`.

**Виправлення:** тепер підраховуються всі спроби — успішні та невдалі.

**Результат:** виявлено 4 чернетки з кількома спробами.

## Висновки

Під час виконання практичної роботи було досліджено спостережуваність AI-компонента, ведення структурованих журналів, відстеження запитів, контроль конфіденційних даних, облік вартості генерації, кешування та обмеження денного бюджету.

Реалізовані механізми дозволяють пов'язувати події за `request_id` і `draft_id`, аналізувати помилки повторних спроб, визначати фактичні витрати та оцінювати ефективність кешування.

Тестування показало, що кешування скорочує час обробки й витрати на реальні виклики провайдера. Контроль бюджету блокує нові виклики після вичерпання ліміту, а збереження стану забезпечує його відновлення після перезапуску.

Також було виправлено облік вартості часткових відповідей, форматування повідомлень про бюджет, хибні попередження та підрахунок повторних спроб.

Отже, спостережуваність і контроль ресурсів є важливими складовими надійного AI-компонента, оскільки забезпечують прозорість роботи, контроль витрат і можливість швидко знаходити технічні проблеми.
