# ПР11. Спостережуваність і контроль ресурсів AI-компонента

Помічник оператора «Сузірʼя» з ПР10, доповнений структурованим журналом, кешем відповідей, денним лімітом витрат і аналізом журналу.

## Що зроблено

| Модуль | Що робить |
|---|---|
| `app/telemetry.py` | JSON Lines, `request_id_var`, приглушення логерів `httpx`, `httpcore`, `openai` |
| `app/costs.py` | Перетворення токенів у вартість, оцінка без `usage` з `cost_estimated=true` |
| `app/cache.py` | Ключ `sha256`, TTL, файл `state/cache.json`, параметр `fresh`, лічильники |
| `app/budget.py` | Денний ліміт, `WARN_AT`, файл `state/budget.json`, атомарний запис |
| `app/gateway.py` | Кеш → бюджет → провайдер → вартість → кеш; журнал `llm.attempt` |
| `app/jobs.py` | `copy_context`, `fresh`, `cached`/`cost`, скасування `cancel` без гонки |
| `app/drafting.py` | `PROMPT_VERSION`, `_PROMPT_HASH`, метадані з довжинами та хешем |
| `app/providers/openai_compat.py` | `usage` у streaming, `cached_tokens`, fallback без `stream_options` |
| `app/providers/mock.py` | Правдоподібний `usage`, `mid_stream`, `partial_text_len` |
| `app/limits.py` | Ковзне вікно 60 секунд, `rate_limit.rejected` у журналі |
| `app/main.py` | `X-Request-ID` у кожній відповіді, обробники помилок |
| `eval/analyze.py` | Шість розділів аналізу: `summary`, `slow`, `failed`, `repeated`, `spend`, `cache` |
| `scripts/run_all.ps1` | Автоматичний запуск сценаріїв 2, 3, 7, 8, 13–14, 18 |
| `scripts/run_openai.ps1` | Окремий запуск сценарію 17 на Gemini |

## Як запустити

### 1. Підготовка середовища

Відкрий PowerShell і виконай команди:

```powershell
cd pr11

python -m venv .venv

.\.venv\Scripts\Activate.ps1

pip install -r requirements.txt

Copy-Item .env.example .env
```

Заповни `LLM_API_KEY` у файлі `.env` або встанови `LLM_PROVIDER=mock`, щоб працювати без ключа API.

Перевір налаштування:

```powershell
python check_env.py
```

### 2. Запуск застосунку

```powershell
python -m uvicorn app.main:app --reload
```

Відкрий у браузері:

[http://127.0.0.1:8000](http://127.0.0.1:8000)

Сторінка містить панель витрат, кешу та бюджету.

### 3. Запуск тестових сценаріїв

**Автоматичний запуск на mock-провайдері:**

```powershell
.\scripts\run_all.ps1
```

**Ручний запуск сценаріїв:**

Без кешу:

```powershell
python eval\replay.py --orders 12 --seed 1 --out eval\s07-nocache.json
```

З кешем:

```powershell
python eval\replay.py --orders 12 --seed 1 --out eval\s08-cache.json
```

Порівняння результатів:

```powershell
python eval\replay.py --compare eval\s07-nocache.json eval\s08-cache.json
```

Докладні інструкції наведено у файлі `eval/README.md`.

### 4. Аналіз журналу

Повний аналіз:

```powershell
python eval\analyze.py
```

Аналіз окремих розділів:

```powershell
python eval\analyze.py --section slow
python eval\analyze.py --section failed
python eval\analyze.py --section repeated
python eval\analyze.py --section spend
python eval\analyze.py --section cache
```

## Ключові технічні рішення

| Питання | Рішення | Обґрунтування |
|---|---|---|
| Які події записувати | `http.request`, `draft.*`, `llm.attempt`, `budget.warning`, `rate_limit.rejected` | Фіксуються зміни стану, а не кожен фрагмент генерації |
| Які дані не записувати | Ключі, текст звернень, факти, повний prompt | Захист персональних даних і секретів |
| Як передавати `request_id` у фон | `copy_context` і `metadata` | Збереження контексту запиту |
| Як контролювати версію prompt | Рядок `PROMPT_VERSION` і хеш `_PROMPT_HASH` | Зручна ідентифікація версії та виявлення змін |
| Як обчислювати вартість без `usage` | Оцінка за текстом, `cost_estimated=true` | Урахування можливих витрат замість безумовного нуля |
| Що включати в ключ кешу | `provider`, `model`, `prompt_version`, `messages`, `temperature`, `max_tokens` | Урахування параметрів, що впливають на генерацію |
| Як працює `fresh` | Пропускає `cache.get`, але виконує `cache.put` | Нова чернетка оновлює запис у кеші |
| Як контролювати бюджет | `check` перед спробою, `record` після | Контроль витрат, зокрема за часткових відповідей |
| Як зберігається бюджет | `state/budget.json` | Збереження стану після перезапуску |
| Як обробляються бюджетні відмови | HTTP 429, `Retry-After`, `kind=budget` | Інформування оператора про вичерпання ліміту |
| Як рахуються повторні спроби | Ураховуються успішні та невдалі спроби | Коректна статистика повторних викликів |

## Результати тестування

Детальні результати наведено у файлі `eval/conclusions.md`.

### Сценарій 2. Повторні спроби

- Оброблено 10 замовлень.
- 9 чернеток завершилися успішно, 1 — помилкою.
- Зафіксовано 16 спроб звернення до провайдера.
- Повторні спроби допомогли завершити 3 із 4 чернеток, у яких перша спроба була невдалою.

### Сценарії 7 і 8. Кешування

- Оброблено 12 замовлень.
- З кешем отримано 5 влучань.
- Кількість звернень до провайдера зменшилася з 12 до 7.
- Фактичні витрати зменшилися з `$0.004078` до `$0.002709` — приблизно на 34 %.
- Сумарний час обробки скоротився на 41 %.

### Сценарії 13 і 14. Контроль бюджету

- Перші 9 замовлень завершилися успішно.
- Витрати досягли `$0.003018` за ліміту `$0.003`.
- Наступні 11 замовлень були відхилені з `kind=budget`.
- Після перезапуску застосунку стан бюджету зберігся.

### Сценарій 18. Переривання потоку

- Виконано 9 спроб для 3 замовлень.
- Усі замовлення завершилися помилкою.
- Оцінена вартість часткових відповідей становила `$0.000027`.
- Витрати невдалих спроб були враховані в журналі.

## Висновки

У ПР11 реалізовано механізми спостережуваності та контролю ресурсів AI-компонента: структуроване журналювання, ідентифікацію запитів, розрахунок вартості, кешування відповідей, контроль денного бюджету та аналіз помилок.

Тестування продемонструвало, що кешування зменшує кількість викликів провайдера, витрати та час обробки. Контроль бюджету обмежує подальші платні запити після вичерпання ліміту, а збереження стану забезпечує відновлення після перезапуску.

Отримані результати підтверджують важливість журналювання, моніторингу витрат і аналізу повторних спроб для забезпечення надійної роботи AI-компонента.

## Чекліст самоперевірки

- [x] `logs/app.jsonl` — один рядок JSON на подію; запис звертання до провайдера містить ідентифікатори запиту й чернетки, клієнта, провайдера, модель, версію prompt, спробу, час до першого фрагмента й разом, статус або вид збою, запасний варіант, токени, вартість, кеш.
- [x] Кожна відповідь API має заголовок `X-Request-ID`; тіло помилки містить `request_id`; за ним знаходяться всі записи чернетки, включно з фоновими.
- [x] У журналі немає ключа, тексту звернення, фактів з іменами й номерами, повного prompt — перевірено `grep`.
- [x] Вартість рахується за `usage` і цінами з `.env`; без `usage` — оцінка з позначкою; оператор бачить вартість чернетки.
- [x] Ключ кешу охоплює провайдера, модель, версію prompt, повідомлення, параметри генерації; TTL діє; результат з кешу позначений і не списує бюджет; «Повторити» оминає кеш; `CACHE_ENABLED=0` вимикає кеш без змін у коді.
- [x] Бюджет: попередження на `BUDGET_WARN_AT` видно на сторінці й у журналі; після вичерпання — помилка виду `budget` з часом відновлення, не 500; перезапуск не обнуляє витрат.
- [x] `eval/analyze.py` показує повільні (медіана, p95, найдовші), невдалі за видом, повторні (ключ кешу, спроби), витрати за день і модель, частку влучань.
- [x] Один потік `eval/replay.py` прогнано без кешу і з кешем; порівняно звертання, токени, вартість, тривалість.
- [x] Шлюз викликає `cache`, `budget`, `costs` і `logging`, не знаючи їхньої будови; веб-рівень не знає про ціни й токени; налаштування — з `.env`.
- [x] Сценарії з `eval/` прогнано, у тому числі на справжньому провайдері з фактичним `usage`; висновки записано.
- [x] Ключ не потрапив ані в код, ані в репозиторій, ані в журнал.
