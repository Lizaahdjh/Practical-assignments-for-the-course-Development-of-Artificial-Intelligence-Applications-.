# ПР4. Керування контекстом і structured output

Помічник служби підтримки інтернет-магазину «Сузірʼя» з ПР3, тепер
**діалоговий** і **придатний для програмної обробки**: відповідь моделі —
це структурований обʼєкт за JSON Schema, а запит — зібраний контекст
(інструкція + правила + історія + звернення), а не одне повідомлення.

## Мета

- Зробити помічника діалоговим: історія передається моделі; факт,
  названий на початку, використовується наприкінці без перепитування.
- Спроєктувати системну інструкцію як специфікацію: роль, обмеження,
  формат результату, 2–3 приклади межових випадків.
- Отримувати відповідь моделі у структурованому форматі за JSON Schema
  й перевіряти її програмно **до** того, як вона потрапить до веб-рівня.
- Вміщати історію розмови в бюджет токенів із конфігурації.
- Порівняти три способи керувати моделлю (нечіткий запит, структурований
  prompt, context engineering) на власному наборі звернень і класифікувати
  типові помилки моделі.

## Що змінилося порівняно з ПР3

| Було в ПР3 | Стало в ПР4 |
|---|---|
| Вільний текст у відповіді | Структурований JSON за схемою (`app/schema.py`) |
| Одне повідомлення | Історія розмови `user`/`assistant` |
| Без бюджету токенів | `LLM_TOKEN_BUDGET`, скорочення історії (`fit_budget`) |
| Один збій — мережа | Плюс новий збій — невалідна відповідь (`LLMSchemaError`) |
| Сторінка показує текст | Сторінка показує відповідь + картку звернення + службові дані |
| Правила + звернення | Правила + **історія** + звернення окремими частинами |
| Схема не передається провайдеру | `response_format` зі схемою; fallback на текстовий JSON |

## Схема відповіді помічника

Файл `app/schema.py`. Описана pydantic-моделлю `AssistantReply`; з неї
генерується JSON Schema для `response_format` і нею ж перевіряється те,
що повернула модель.

| Поле | Тип | Обовʼязкове | Опис |
|---|---|---|---|
| `reply` | `str` | так | Текст відповіді для клієнта |
| `topic` | `enum` | так | `order` / `delivery` / `payment` / `return` / `warranty` / `support` / `other` |
| `grounded_in_rules` | `bool` | так | Чи відповідь спирається на правила |
| `needs_clarification` | `bool` | так | Чи потрібне уточнення |
| `escalate_to_human` | `bool` | так | Підказка моделі щодо оператора |
| `order_number` | `str \| null` | ні | 6 цифр, якщо клієнт його назвав |

### Що перевіряється кодом додатково

- **`order_number`** — має справді зустрічатися в тексті розмови
  (`schema.verify_order_number`). Якщо модель вигадала номер — поле
  очищується, факт пишеться в журнал.
- **`escalate_to_human`** — фінальне рішення ухвалює код, а не модель:
  якщо `needs_clarification=true` або `grounded_in_rules=false`, або номер
  не підтвердився — ставимо `true` (див. `llm.ask`).

## Ключові рішення

| Питання | Рішення |
|---|---|
| Що класти в історію з боку помічника | лише текст `reply`, не весь JSON |
| Де живе історія | у клієнта; сервер не зберігає стан |
| Що скорочувати першим | середину; перша і остання репліки зберігаються завжди |
| Що робити з невалідною відповіддю | 1 повтор із текстом помилки → `LLMSchemaError` (502) |
| Чи передавати схему провайдеру | так, через `response_format`; fallback на текстовий JSON |
| Чи довіряти `grounded_in_rules` | як самозвіт моделі; фінальне рішення ухвалює код |
| Що зараховувати в `elapsed` | час із повторами; окремо `attempts` |

Як користуватися сторінкою

Введіть звернення й натисніть «Надіслати».

Ліва колонка — діалог: ваші репліки і відповіді помічника.

Права колонка — картка звернення, яка заповнюється в міру розмови
(усі поля схеми, крім reply), і службові дані: модель, час, токени.

Кнопка «Нова розмова» очищує історію, картку й чат.

Порівняння трьох конфігурацій

powershell

python compare/run.py

svgsvg

Скрипт проганяє 6 звернень і 2 діалоги (по 3 репліки) за трьох
конфігурацій — усього 36 викликів — і формує два файли:

compare/results.json — повні відповіді моделі по кожному прогону;

compare/findings.md — зведені таблиці, зібрані невдалі відповіді,
класифікація помилок за типами.

Три конфігурації

Нечіткий запит (vague) — текст клієнта з однорядковою
інструкцією; без формату, без правил, без історії.

Структурований prompt (structured) — повна інструкція з
обмеженнями, форматом і прикладами; без правил магазину, без історії.

Context engineering (context) — та сама інструкція + правила з
context.md + історія в межах бюджету + перевірка за схемою.

Автоматичні перевірки у run.py

Для кожної відповіді скрипт перевіряє:

schema_ok — чи пройшла схему;

topic_ok — чи тема відповідає очікуванню для виду звернення;

grounded_ok — чи grounded_in_rules відповідає очікуванню;

hallucination — чи вигадала модель факт (за прапорцем grounded);

order_in_history — чи названий номер справді є в розмові;

recall_ok — (для діалогів) чи втримано факт на репліці, де він
потрібен.

## Що ще варто зробити перед здачею

1. **Перевірте `.gitignore`** — має містити `.env`, `.venv/`, `__pycache__/`, `compare/requests.json`, `compare/results.json`, `compare/findings.md`. Останні три — бо вони ваші особисті.

2. **Допишіть у `compare/findings.md` власні висновки** — автоматичні таблиці це добре, але викладач шукатиме ваші спостереження. Додайте 2–3 абзаци: наприклад, чому `structured` вигадав ліміт 5000 грн, а `context` — ні; чому `grounded_in_rules` не можна довіряти наосліп.

3. **Перевірте сторінку в браузері** — вона має показати діалог, картку й службові дані. Якщо хочете, надішліть скріншот помилки, якщо щось не так.

4. **Підготуйтеся до контрольних питань** — вони всі є в `ПР4.pdf`, але основні:
   - що гарантує `response_format` і що все одно перевіряєте ви?
   - чому `grounded_in_rules` — не істина, а самозвіт?
   - чому першу репліку не можна відкидати ніколи?
   - чому фінальне `escalate_to_human` ухвалює код, а не модель?
