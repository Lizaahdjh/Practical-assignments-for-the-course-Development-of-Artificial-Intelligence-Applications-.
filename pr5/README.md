# ПР5. Семантичний пошук у колекції документів

Матеріали до пʼятої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР5.pdf`, виданому до заняття.

## Задача коротко

База знань магазину «Сузірʼя» виросла: замість одного `context.md` — шістнадцять документів у папці `docs/`: правила, інструкції до товарів, відповіді на часті запитання, довідники, внутрішня інструкція. У запит до моделі вони вже не вміщуються, та й не потрібні всі одразу. Потрібен **пошук**, який за запитом користувача знаходить ті кілька фрагментів, що стосуються справи.

Ви будуєте його самі: ділите документи на фрагменти, перетворюєте фрагменти на вектори локальною моделлю ембедінгів, зберігаєте індекс на диску, а за запитом повертаєте top-k найближчих фрагментів з оцінкою схожості. Метадані документів стають фільтрами. Поруч — пошук за ключовими словами по тих самих фрагментах, щоб було з чим порівняти.

Наприкінці — порівняння двох способів на власному наборі запитів із відомими відповідями. У ПР6 цей пошук стане частиною помічника, який відповідає мовною моделлю.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Каркас застосунку |
| `docs/` | Колекція документів магазину з метаданими; опис — у `docs/README.md` |
| `ingest.py` | Побудова індексу: читає `docs/`, викликає ваші модулі, зберігає результат |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок налаштувань: модель, top-k, поріг, параметри поділу |
| `check_env.py` | Перевірка середовища: Python, пакети, колекція, завантаження моделі й пробне кодування |
| `compare/` | Порівняння семантичного пошуку з пошуком за ключовими словами |

```
app/
├─ main.py                веб-рівень: сторінка, /api/status, /api/search
├─ documents.py           колекція: метадані (готово), поділ на фрагменти (заготовка)
├─ embeddings.py          модель ембедінгів — заготовки
├─ index.py               векторний індекс: збирання, збереження, пошук — заготовки
├─ keyword.py             пошук за ключовими словами — заготовки
└─ templates/index.html   сторінка з двома стовпцями результатів і фільтрами
```

Каркас дає структуру проєкту й робочий веб-рівень: сторінка надсилає запит із режимом, top-k, порогом і фільтрами та показує результати обох способів поруч з оцінками, джерелом і метаданими. Розбір блоку метаданих у файлах теж готовий — це формат даних, а не предмет роботи. **Реалізації в ньому немає:** поділ на фрагменти, модель, індекс і пошук за словами підіймають `NotImplementedError`, а ендпоінт не обробляє помилок.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
python check_env.py
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`.

**Запустіть `check_env.py` заздалегідь.** Разом із `sentence-transformers` встановлюється `torch` — це кілька сотень мегабайт, а при першому запуску скрипт завантажує ще й модель ембедінгів (близько півгігабайта). Робити це вперше на занятті — втратити пів пари. Скрипт кодує три речення й показує, наскільки схожими їх вважає модель: перефразування має бути ближчим за стороннє речення.

Ключ доступу до API в цій роботі не потрібен, якщо ви рахуєте ембедінги локальною моделлю. Якщо вирішите рахувати їх через API, візьміть ключ із ПР3 — зразок рядків є у `.env.example`.

Побудова індексу й запуск застосунку з папки `pr5`:

```bash
python ingest.py
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 — сторінка вже працює, а сам пошук завершиться помилкою, доки ви не реалізуєте модулі.

## Що очікує сторінка

При відкритті сторінка викликає `GET /api/status` і показує, чи збудовано індекс. Пошук — `POST /api/search` з обʼєктом `{"query": "...", "mode": "both", "top_k": 5, "filters": {"category": "інструкція"}, "threshold": null}`; режим — `semantic`, `keyword` або `both`.

У відповідь сторінка очікує `{"semantic": [...], "keyword": [...], "elapsed": {"semantic": 0.05, "keyword": 0.002}}`, де кожне влучення — `{"score": 0.87, "text": "...", "source": "файл.md", "metadata": {...}}`. Поля `metadata` показуються як є: додасте заголовок розділу — він зʼявиться на сторінці. Якщо назвете поля інакше — змініть сторінку, вона ваша.

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/documents.py` → `split` | Поділити текст документа на фрагменти: межі, розмір, перекриття, що додати до тексту й метаданих фрагмента |
| `app/embeddings.py` → `get_model`, `embed_passages`, `embed_query` | Обрати модель і закодувати фрагменти й запит — з урахуванням того, що вимагає картка моделі |
| `app/index.py` → `build`, `save`, `load`, `search` | Зібрати індекс, зберегти на диск разом із назвою моделі, прочитати; знайти top-k за схожістю з фільтрами й порогом |
| `app/keyword.py` → `tokenize`, `build`, `search` | Пошук за ключовими словами по тих самих фрагментах у тому самому форматі |
| `app/main.py` → `api_search` | Обробити збої: порожній запит, відсутній індекс, невідомий режим або фільтр |
| `compare/` | Набір запитів з очікуваними документами, прогін обома способами, одна зміна, висновки |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Чекліст самоперевірки

- [ ] `python ingest.py` будує індекс з усіх документів `docs/` і зберігає його на диск разом із назвою моделі.
- [ ] Фрагменти мають осмислений розмір і межі; у кожного є джерело й метадані документа.
- [ ] Запит перетворюється на вектор тією самою моделлю, що й фрагменти; пошук повертає top-k з оцінкою схожості.
- [ ] Фільтри за метаданими працюють: `audience`, `status`, `category`, `product`.
- [ ] Пошук за ключовими словами працює по тих самих фрагментах і повертає той самий формат.
- [ ] Сторінка показує обидва способи поруч: оцінку, джерело, метадані, текст, час.
- [ ] Застосунок стартує без індексу й каже, що робити; порожній запит і невідомий фільтр не дають 500.
- [ ] Модель створюється один раз; індекс читається при старті, а не на кожен запит.
- [ ] Веб-рівень не знає ані моделі, ані формату індексу.
- [ ] Порівняння проведено на 12–15 запитах з очікуваними документами; одна зміна перевірена окремо; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
