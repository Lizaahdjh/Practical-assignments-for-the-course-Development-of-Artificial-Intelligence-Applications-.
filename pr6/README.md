# ПР6. RAG-помічник за власною базою знань

## Опис проєкту

RAG-помічник служби підтримки інтернет-магазину **«Сузірʼя»** відповідає на питання клієнтів на основі власної бази знань.

Помічник знаходить релевантні фрагменти документів, передає їх мовній моделі разом з інструкцією та формує відповідь із зазначенням джерел.

Якщо необхідної інформації в базі знань немає, помічник повідомляє про це та не вигадує відповідь.

Проєкт реалізує підхід **Retrieval-Augmented Generation (RAG)**, який об'єднує семантичний пошук із ПР5 та мовну модель із ПР3–ПР4.

## Мета роботи

* Перетворити семантичний пошук на повний RAG-конвеєр.
* Відбирати необхідні фрагменти для мовної моделі.
* Обмежувати кількість фрагментів і бюджет токенів.
* Отримувати структуровану відповідь із джерелами.
* Перевіряти посилання на джерела програмно.
* Не допускати вигаданих відповідей, якщо інформації немає в базі.
* Розділяти помилки пошуку та помилки генерації.

## Основні зміни порівняно з ПР5

| ПР5                                   | ПР6                                                     |
| ------------------------------------- | ------------------------------------------------------- |
| Фрагменти переглядає користувач       | Фрагменти передаються мовній моделі                     |
| Показується результат пошуку          | Показується відповідь і джерела                         |
| Поріг лише відсікає слабкі результати | Поріг визначає, чи потрібно викликати модель            |
| Немає відбору контексту               | Додано `retrieval.retrieve` і `retrieval.build_context` |
| Немає генерації                       | Додано `llm.ask`                                        |
| Немає джерел                          | Додано посилання `[N]`                                  |
| Немає ознаки знайденої відповіді      | Додано поле `found`                                     |

## Схема відповіді моделі

Відповідь описана Pydantic-моделлю `ModelReply` у файлі `app/schema.py`.

| Поле      | Тип         | Опис                              |
| --------- | ----------- | --------------------------------- |
| `answer`  | `str`       | Відповідь клієнту                 |
| `sources` | `list[int]` | Номери використаних фрагментів    |
| `found`   | `bool`      | Чи знайдена відповідь у контексті |

Додатково код перевіряє:

* чи існують зазначені номери джерел;
* чи не встановлено `found=true` без джерел;
* чи немає суперечності `found=false` разом із джерелами;
* чи застосовані обов'язкові фільтри `audience=клієнти` та `status=чинний`.

## Основні налаштування

У `.env` використовуються такі параметри:

```env
LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
LLM_API_KEY=<ваш ключ з Google AI Studio>
LLM_MODEL=gemini-3.5-flash-lite
LLM_TEMPERATURE=0.1
LLM_MAX_TOKENS=700
LLM_TIMEOUT=30

EMBEDDING_MODEL=intfloat/multilingual-e5-small
CHUNK_SIZE=600
CHUNK_OVERLAP=100
SEARCH_TOP_K=8
SIMILARITY_THRESHOLD=

RAG_CONTEXT_CHUNKS=4
RAG_CONTEXT_BUDGET=1500
```

Для RAG використовується максимум 4 фрагменти контексту та бюджет 1500 токенів. Температура моделі встановлена на рівні `0.1`, щоб відповідь була максимально прив'язана до документів.

## Запуск у Windows PowerShell

```powershell
cd "шлях-до\pr6"

python -m venv .venv

.venv\Scripts\python.exe -m pip install -r requirements.txt

copy .env.example .env

notepad .env
```

У `.env` потрібно вказати `LLM_API_KEY`.

Далі перенести модулі пошуку з ПР5:

```powershell
copy ..\pr5\app\documents.py app\documents.py
copy ..\pr5\app\embeddings.py app\embeddings.py
copy ..\pr5\app\index.py app\index.py
copy ..\pr5\app\keyword.py app\keyword.py
```

Перевірити середовище:

```powershell
.venv\Scripts\python.exe check_env.py
```

Побудувати індекс:

```powershell
.venv\Scripts\python.exe ingest.py
```

Запустити застосунок:

```powershell
.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Після запуску відкрити:

```text
http://127.0.0.1:8000/
```

## Використання

1. Ввести питання у поле запиту.
2. Натиснути **«Запитати»**.
3. Отримати відповідь помічника.
4. Переглянути джерела, використані для відповіді.
5. За необхідності розгорнути блок **«Що бачила модель»**.

На сторінці також відображаються службові дані: модель, час пошуку, час генерації та кількість токенів.

Якщо відповідь була в контексті, але модель відповіла неправильно — це проблема генерації. Якщо потрібної інформації не було серед отриманих фрагментів — це проблема пошуку.

## Перевірка роботи

Для оцінювання використовується набір із 12–15 питань.

```powershell
copy eval\questions.example.json eval\questions.json

.venv\Scripts\python.exe eval\run.py
```

Скрипт формує `eval/results.json` та `eval/findings.md`.

Перевіряються такі показники:

* `expected_in_context`;
* `found_answer`;
* `correct_refusal`;
* `wrong_refusal`;
* `wrong_answer`;
* `false_source`.

Помилки поділяються на помилки пошуку та помилки генерації.

## Експеримент зі зміною параметра

Для порівняння результатів потрібно:

```powershell
copy eval\results.json eval\results.base.json
```

Потім змінити:

```env
RAG_CONTEXT_CHUNKS=4
```

на:

```env
RAG_CONTEXT_CHUNKS=6
```

Після цього повторно запустити:

```powershell
.venv\Scripts\python.exe eval\run.py
```

Порівняти `expected_in_context`, `found_answer` та кількість токенів до і після зміни.

## Обробка помилок

| Помилка                    | HTTP | Обробка                      |
| -------------------------- | ---: | ---------------------------- |
| Порожнє питання            |  400 | `HTTPException`              |
| Занадто довге питання      |  400 | `HTTPException`              |
| Індекс не збудовано        |  503 | `HTTPException`              |
| Невалідна відповідь моделі |  502 | `LLMSchemaError`             |
| Таймаут моделі             |  504 | `LLMTimeoutError`            |
| Перевищення лімітів        |  429 | `LLMRateLimitError`          |
| Недоступність сервісу      |  503 | `LLMServiceUnavailableError` |
| Помилка автентифікації     |  502 | `LLMAuthError`               |
| Модель не знайдена         |  502 | `LLMError`                   |

Для помилок моделі передбачені повторні спроби з backoff, а невалідна відповідь проходить повторну перевірку.

## Безпека

* API-ключ зберігається тільки у `.env`.
* `.env` не повинен потрапляти до репозиторію.
* Внутрішні документи з `audience=персонал` не передаються моделі під час запиту клієнта.
* Архівні документи з `status=архів` також відфільтровуються кодом.
* Користувач не може вимкнути ці фільтри через веб-інтерфейс.

## Чекліст

* [] Помічник відповідає на питання на основі бази знань.
* [] Відповідь містить джерела.
* [] За відсутності інформації помічник не вигадує відповідь.
* [] Внутрішні документи не потрапляють до моделі.
* [] Контекст має обмежену кількість фрагментів і бюджет токенів.
* [] Відповідь перевіряється за Pydantic-схемою.
* [] Джерела перевіряються програмно.
* [] Веб-сторінка показує відповідь, джерела та службові дані.
* [] Реалізована обробка помилок.
* [] API-ключ не зберігається у коді або репозиторії.
* [] Виконано тестування на 12–15 питаннях та заповнено `findings.md`.

## Зв'язок із попередніми роботами

* **ПР3** — інтеграція мовної моделі через API та обробка помилок.
* **ПР4** — structured output, JSON Schema та перевірка відповіді.
* **ПР5** — семантичний пошук і модулі роботи з індексом.

ПР6 об'єднує ці компоненти у повний RAG-конвеєр: **пошук → відбір → передача контексту → генерація → перевірка → відповідь із джерелами**.
