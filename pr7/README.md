# ПР7. Мультимодальний аналіз і структуроване вилучення даних

Застосунок для магазину **«Сузірʼя»**, який за зображенням рахунку на оплату вилучає заданий набір полів за допомогою мультимодальної моделі. Після цього код перевіряє отримані дані за програмними правилами та визначає рішення: `auto`, `review` або `reject`.

## Мета

* Приймати зображення рахунку та повертати структуровані дані.
* Перевіряти відповідь моделі за схемою та програмними правилами.
* Контрольовано обробляти відсутні та невпевнені значення.
* Ухвалювати рішення `auto` / `review` / `reject` у коді, а не моделлю.
* Порівнювати якісні та навмисно погіршені зображення.
* Розрізняти помилки, які виявляються правилами, та тихі помилки моделі.

## Що змінилося порівняно з ПР6

| Було в ПР6                   | Стало в ПР7                                                            |
| ---------------------------- | ---------------------------------------------------------------------- |
| Текстові документи           | Зображення рахунків                                                    |
| Модель без зображень         | Мультимодальна модель (vision)                                         |
| Текстовий запит              | Запит із `image_url`                                                   |
| Перевірка за схемою          | Схема + програмні правила                                              |

| Рішення `found` / `escalate` | Рішення `auto` / `review` / `reject`                                   |
| Один шар перевірки           | Три шари: схема → правила → рішення                                    |

### Призначення основних модулів

* `main.py` — веб-рівень, сторінка та API.
* `images.py` — перевірка та підготовка зображень.
* `schema.py` — Pydantic-схема відповіді моделі.
* `llm.py` — інструкція, передача зображення моделі та обробка помилок.
* `rules.py` — перевірка IBAN, ЄДРПОУ, арифметики, дат та інших правил.
* `extraction.py` — основний конвеєр та прийняття рішення.
* `index.html` — веб-інтерфейс для розбору рахунків.

## Схема відповіді моделі

У файлі `app/schema.py` відповідь описана Pydantic-моделлю `InvoiceExtraction`.

| Поле                | Тип          | Опис                                                   |
| ------------------- | ------------ | ------------------------------------------------------ |
| `document_type`     | enum         | `рахунок` / `видаткова накладна` / `інше`              |
| `number`            | `str?`       | Номер рахунку                                          |
| `date`              | `str?`       | Дата у форматі `РРРР-ММ-ДД`                            |
| `valid_until`       | `str?`       | Строк дії                                              |
| `supplier`          | `Party`      | `name`, `code`, `iban`                                 |
| `buyer`             | `Party`      | `name`, `code`                                         |
| `items`             | `list[Item]` | Позиції: `name`, `unit`, `quantity`, `price`, `amount` |
| `total_without_vat` | `str?`       | Разом без ПДВ                                          |
| `vat`               | `str?`       | ПДВ                                                    |
| `total`             | `str?`       | До сплати                                              |

Суми передаються як рядки з двома знаками після крапки, наприклад `"123.45"`. Це дозволяє уникнути проблем із `float`.

Якщо значення відсутнє або його неможливо визначити, використовується `null`.

## Програмні правила

У файлі `app/rules.py` реалізовано такі перевірки:

| Правило            | Що перевіряє                                |
| ------------------ | ------------------------------------------- |
| `document_type`    | Чи є документ рахунком на оплату            |
| `missing_required` | Наявність обов'язкових полів                |
| `iban_checksum`    | Коректність IBAN за mod 97                  |
| `iban_registry`    | Відповідність IBAN довіднику постачальників |
| `code_checksum`    | Контрольну суму ЄДРПОУ або РНОКПП           |
| `buyer`            | Чи є покупцем «Сузірʼя Рітейл»              |
| `date_future`      | Чи не є дата майбутньою                     |
| `date_format`      | Правильність формату дати                   |
| `date_order`       | Строк дії не раніше дати рахунку            |
| `arithmetic_line`  | `quantity × price = amount`                 |
| `arithmetic_sum`   | Сума позицій = `total_without_vat`          |
| `arithmetic_vat`   | ПДВ = 20% від суми без ПДВ                  |
| `arithmetic_total` | `total = total_without_vat + vat`           |

Допуск при перевірці округлення становить **0.01 грн**.

## Рішення `auto` / `review` / `reject`

Рішення приймає **код у `app/extraction.py`**, а не мультимодальна модель.

### `reject`

Документ відхиляється, якщо:

* це не рахунок;
* модель не змогла нічого вилучити.

### `review`

Документ передається на перевірку людиною, якщо:

* знайдена хоча б одна помилка;
* пропущено критичне поле;
* дані не пройшли одну з програмних перевірок.

### `auto`

Документ можна автоматично внести до реєстру, якщо:

* немає жодної помилки;
* присутні всі критичні поля:

  * `supplier.iban`;
  * `supplier.code`;
  * `buyer.name`;
  * `total`.

Модель не може самостійно встановити `auto`. Вона лише вилучає дані, а остаточне рішення приймає програмний код.

Навіть текст на зображенні на кшталт «погоджено, не перевіряти» не впливає на рішення системи.

## Налаштування `.env`

```env
# ---- Мовна модель ----
LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
LLM_API_KEY=<ваш ключ з Google AI Studio>
LLM_MODEL=gemini-3.5-flash-lite
LLM_TEMPERATURE=0
LLM_MAX_TOKENS=2500
LLM_TIMEOUT=60

# ---- Зображення ----
UPLOAD_MAX_MB=10
IMAGE_MAX_SIDE=1600
```

Для роботи потрібен API-ключ із Google AI Studio.

Ключ можна перенести з `.env` попередніх практичних робіт.

Модель повинна підтримувати роботу із зображеннями.

Якщо `check_env.py` показує помилку `404`, потрібно перевірити значення `LLM_MODEL` у `.env`.

## Запуск у Windows PowerShell

```powershell
cd "шлях-до\pr7"

# 1. Створення віртуального середовища

# 2. Встановлення залежностей
.venv\Scripts\python.exe -m pip install -r requirements.txt

.venv\Scripts\python.exe check_env.py

```

## Як користуватися сторінкою

1. Вибрати зразок зі списку або завантажити власний файл.
2. Натиснути **«Розібрати»**.
3. Переглянути рішення:

   * у реєстр платежів;
   * на перевірку людині;
   * відхилено.
4. Переглянути причини прийнятого рішення.
5. Переглянути проблеми, знайдені програмними правилами.
6. Переглянути вилучені поля.
7. Переглянути позиції документа.
8. Переглянути службові дані.

Службова інформація містить:

* назву моделі;
* розміри зображення до та після підготовки;
* час виконання окремих етапів;
* кількість використаних токенів.

Для відладки можна розгорнути блок **«Відповідь застосунку повністю»** та переглянути сирий JSON.

## Перевірка на зразках

Для запуску оцінювання використовується:

```powershell
.venv\Scripts\python.exe eval\run.py
```

Скрипт обробляє всі підготовлені зразки та формує:

* `eval/results.json` — повні результати для кожного файлу;
* `eval/findings.md` — зведені таблиці, деталі та місце для висновків.

У наборі використовуються:

* 9 якісних зображень;
* 18 погіршених варіантів;
* власні зразки для додаткової перевірки.

## Безпека

* API-ключ зберігається лише у `.env`.
* `.env` не повинен потрапляти до репозиторію.
* Для інших користувачів використовується `.env.example` без ключа.
* Остаточне рішення приймає код, а не модель.
* Дані, які знаходяться в самому документі, не можуть змінити програмні правила.
* Текст на рахунку, адресований «системі обробки», не повинен впливати на рішення.

## Архітектура перевірки

Обробка документа проходить через три основні рівні:

```text
Зображення рахунку
       ↓
Вилучення даних мультимодальною моделлю
       ↓
Pydantic-схема
       ↓
Програмні правила
       ↓
Рішення
 ┌─────┼─────┐
 ↓     ↓     ↓
auto review reject
```

Такий підхід дозволяє розділити відповідальність:

* модель відповідає за вилучення інформації;
* схема відповідає за форму даних;
* правила відповідають за зміст і коректність;
* код відповідає за остаточне рішення.

## Висновок

ПР7 реалізує мультимодальний конвеєр для автоматичного вилучення даних із рахунків. Основна особливість рішення полягає в тому, що мовна модель використовується лише для отримання структурованої інформації, а перевірка даних і фінальне рішення виконуються програмними правилами.

Такий підхід дозволяє зменшити ризик помилок моделі та чітко розділити автоматичну обробку, ручну перевірку і відхилення документа.
